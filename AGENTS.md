## Canonical user-run validation and startup workflow

When the user asks whether the project works, asks to check startup, reports a blank/nonworking UI, or needs routine post-change verification on Windows, instruct them to double-click **`+ Diagnose Startup.cmd`** in the project root first. This is the single canonical launcher and runs the full v2 diagnostic workflow. Do not routinely make them paste a series of separate PowerShell commands. The full Diagnose Startup workflow checks the pinned Node.js/npm versions and source metadata, restores a missing/mismatched dependency tree with `npm ci`, verifies `npm ls --depth=0`, runs TypeScript checks and the complete test suite, saves production/full npm audit JSON reports, builds the app, explicitly runs `install-electron --no`, verifies the Electron executable/version, then launches Mad Station and reports startup event names confirming the main process, app-ready initialization, window creation, main UI and toolbar renderer loads, renderer failures, and exit status. The final summary explicitly says `NOT ATTEMPTED`, `STARTUP NOT FULLY CONFIRMED`, or `STARTUP CONFIRMED` (including warnings). The console stays open and the timestamped transcript is written under `%LOCALAPPDATA%\MadStation\diagnostics` (TEMP fallback). It does not build the Windows installer; use `+ build installer.cmd` only after validation and manual GUI acceptance. The current tree carries a narrowly scoped local `sprintf-js` maintenance patch at `vendor/sprintf-js-1.1.4+madstation.1.tgz`; its SHA-512 is pinned in package-lock and verified by `scripts/check-dev-environment.mjs` and the Diagnose Startup workflow. The upstream advisory still lists no official patched release, so this is a documented private maintenance patch, not an upstream version. Do not globally force `@electron/get@5` into Electron Builder 26 (its downloader API is breaking) and do not use the audit's forced `electron-builder@26.5.0` downgrade. The diagnostic still treats any remaining/unreadable audit findings as release blockers. Remove the local override only after a compatible official patch has been reviewed and tested. If the launcher fails, ask for the final summary and relevant log—not a retyped list of every command. The CMD launcher runs `scripts/check-diagnose-startup-syntax.ps1`, which parses `scripts/diagnose-startup.ps1` with the PowerShell AST parser and stops before the full workflow if syntax errors exist. Update the diagnostic script, syntax preflight, and focused release test together whenever this workflow changes. In Windows PowerShell 5.1, do not pipe raw npm v3 `package-lock.json` into `ConvertFrom-Json`: its `packages[""]` root key can fail parsing. The diagnostic uses Node's JSON parser to move that entry read-only to `rootPackage` before PowerShell parses the projection; keep this compatibility handling and its regression assertions.
